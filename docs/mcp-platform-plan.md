## 0. 一句话说清这个系统在干什么

**它是 MCP 世界的"应用商店 + 遥控器 + 审计员"。**

- **应用商店**：用户从目录里挑一个 MCP 服务器（或自己填配置）装进来。
- **遥控器**：装进来之后能看它提供了哪些工具、能单独开关某个工具、能重启、能删掉。
- **审计员**：谁装了什么、谁调了哪个工具、传了什么参数、成功还是失败，全部留痕。

技术上说，你要做的是**一个 MCP 主机端（Host / Client）的管理平面**。注意和"写 MCP 服务器"是相反的方向：你不生产工具，你**消费**别人的工具并管好它们。

## 2. 三个必须先拍板的设计决策

这三个不定，后面全是返工。我给出建议和理由，你拍板。

### 决策 1（最关键）：MCP 连接放在哪个进程里？

**问题**：你现在用 uvicorn 起 FastAPI。如果开了 `--workers > 1`，每个 worker 进程都是独立的。用户 A 在界面上"添加了一个 MCP 服务器"，这个动作只落在处理请求的那个 worker 上——其他 worker 不知道，子进程也可能随 worker 重启而丢失。而 stdio 传输的 MCP 服务器是**子进程**，天然绑定在启动它的那个进程上。

**三个方案**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 单实例集中管理（推荐）** | MCP 连接只由一个**专用进程/Celery worker**持有，Web 层通过 Redis 发指令、读状态 | 状态唯一、子进程不会漏、可水平扩展 Web 层 | 需要引入"控制指令 + 状态回传"通道，实现复杂度中等 |
| B. 每 worker 自治 | 每个 worker 自己连全量服务器，数据库是唯一真相，靠轮询/消息同步变更 | 实现简单 | N 个 worker × M 个服务器 = N×M 个子进程，资源爆炸；调用结果不一致 |
| C. 连接按需即用即弃 | 每次调用临时起子进程，用完就关 | 无状态、最简单 | 每次调用都要冷启动（npx 拉包可能几秒），体验差；不适用 Streamable HTTP 长连接 |

**建议选 A**，M1 阶段就把连接管理层抽象干净（哪怕 M1 先跑单 worker，接口也按 A 设计），避免后期推翻重来。

### 决策 2：服务器归谁所有？

你要的是"用户管理**自己接入**的工具"，但企业内网通常也需要管理员提供公共工具。建议**两种并存**：

- `owner_type = system | user`
  - **system**：管理员接入，全员（或按角色/部门）可见可用，凭据是系统凭据，用户无需配置。
  - **user**：用户自己接入，只有自己可见，凭据是自己的 key。
- 管理员可开关"是否允许普通用户自行接入"（企业合规刚需）。
- 前端列表分两个 Tab：「公共工具」「我的工具」。

### 决策 3：工具怎么进 Agent 的工具箱？

现在是全局 `TOOL_REGISTRY`，加进来就对所有人可见。改造要点：

- **命名空间**：工具名统一加前缀，如 `mcp_<server_slug>__<tool_name>`，避免两个服务器都叫 `search` 时互相覆盖。
- **冲突检测**：新增服务器时如果撞名，明确提示并让用户选（保留/改名/停用）。
- **按人过滤**：用户发起会话时，只注入"系统公共工具 ∩ 其角色权限"+"他自己的工具"。
- **粒度开关**：不仅能关掉整个服务器，还能单独禁用某个工具（合规场景常用，比如禁掉 `delete_*`）。
- ⚠️ **上下文膨胀预警**：接 20 个服务器可能有 300+ 个工具，全塞进提示词会爆上下文，也会拖慢模型。你项目里已有 `bench_context_trim.py`，说明你关注过这个问题。M5 阶段需要"工具检索/分组按需加载"，不要一次性全量注入。

## 3. 技术选型结论：不用纠结，但有两处要升级

之前对比过 Go / Node / Python 三套。结论很明确：**继续用 Python**——你的整个后端、ORM、权限、前端都在这套栈上，换语言等于重写。

**好消息**：你装的 `mcp` 2.1.1 已经是 **v2 稳定线**，而 v2 的关键能力正好解决你的痛点：

| v2 能力 | 对你的用处 |
|---|---|
| 同时说 2026-07-28 和 2025-11-25 及更早版本，`Client(target)` **自动协商版本** | 生态里大量服务器还没迁移到新规范，你能自动兼容，不用自己写双栈 |
| 一等公民 `Client` 对象：`Client(url)` / `Client(stdio_client(...))` / `Client(服务器对象)` | 一套代码同时支持 stdio 和 Streamable HTTP |
| `client.protocol_version` / `server_capabilities` / `server_info` 直接可读 | 界面上展示"对端协议版本、能力"有了现成数据源 |
| 内置 OpenTelemetry 追踪 | 调用链排查和审计可直接对接 |
| `mcp_types` 独立类型包 | 前后端共享工具 schema 定义 |

**需要注意的 v2 破坏性变化（影响你现有代码）**：

1. `FastMCP` 已改名 `MCPServer`（`from mcp.server import MCPServer`），`mcp_servers/calculator_server.py` 若用了旧 import 需改。
2. **服务端不能再反过来调客户端**：新规范下 `ctx.elicit()` 在 2026 连接上会抛 `NoBackChannelError`，改为 MRTR（多轮往返）机制。你现在用 `Resolve(...)` 或 `InputRequiredResult` 来处理"工具执行中需要用户补充输入/确认"。⚠️ 这条会直接影响你 Agent 的**人机确认流程**（比如危险操作二次确认），M2 必须验证现有链路。
3. `mcp.types` 已移除 → 改用 `mcp_types`。
4. `ping` 被移除，健康检测要自己实现（不能靠 ping）。
5. `roots` / `sampling` / logging 已废弃（12 个月过渡期），新代码不要再用。

## 4. 架构设计

```
┌─────────────────────────────────────────────────────────────┐
│  Vue3 管理控制台（frontend）                                  │
│  公共工具 / 我的工具 / 新增向导 / 连通性测试 / 工具开关 / 日志  │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST / SSE
┌───────────────────────────▼─────────────────────────────────┐
│  FastAPI 管理 API（backend/app/mcp/ 新增 admin 路由）         │
│  服务器 CRUD · 凭据写入 · 审批 · 工具开关 · 诊断 · 审计查询    │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  连接编排层（新增，按决策 1 方案 A 设计）                      │
│  · 连接池：server_id → Connection 句柄                        │
│  · 生命周期：启动 / 停止 / 重启 / 健康检测 / 自动重连          │
│  · 传输适配：stdio 子进程 | Streamable HTTP                   │
│  · 工具清单发现 + 缓存（注意新规范的 ttlMs / cacheScope）      │
│  · 指令通道：Web 层 --Redis--> 编排层；状态回写 DB/Redis       │
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  持久化层（PostgreSQL）                                       │
│  mcp_server · mcp_credential · mcp_tool · mcp_invocation_log │
│  复用现有：users / roles / permissions                        │
└─────────────────────────────────────────────────────────────┘

        Agent 调用链路（改动最小的一层）：
   planner/executor ──> TOOL_REGISTRY ──> mcp_adapter ──> 连接编排层 ──> 外部 MCP
                            ▲
                    （按用户过滤 + 命名空间 + 启停过滤 + 审计埋点）
```

**一条完整数据流**（"用户装了一个 MCP 服务器"）：

1. 用户在前端填配置（类型选 stdio / HTTP，填启动命令或 URL，填需要的 key）
2. 后端校验 → 凭据加密入库 → 服务器记录入库（状态 `pending`）
3. （若开启审批）生成审批单，管理员通过后才进入下一步
4. 编排层收到指令 → 建立连接 → 调用 `tools/list` 拉取工具清单 → 写入 `mcp_tool` 表
5. 状态置 `active`，前端展示工具列表和每个工具的开关
6. 用户发起会话时，按"公共 ∩ 权限 + 个人"过滤后注入 Agent 工具箱
7. 每次调用写 `mcp_invocation_log`（参数脱敏、耗时、结果摘要、成功与否）

## 5. 核心数据模型（Alembic 迁移）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `mcp_server` | id, slug(唯一), name, owner_type(system/user), owner_id, transport(stdio/http), command, args(JSON), url, headers_tpl(JSON), env_tpl(JSON), status(pending/active/error/disabled), enabled, protocol_version(协商结果), last_health_at, last_error | 服务器定义 |
| `mcp_credential` | id, server_id, ref_name(如 `API_KEY`), encrypted_value, version, rotated_at | 凭据单独表，加密存储；`env_tpl` 里只放 `${API_KEY}` 引用 |
| `mcp_tool` | id, server_id, raw_name, namespaced_name(唯一), description, input_schema(JSON), enabled, discovered_at, cache_ttl_ms | 工具清单快照，支持单工具开关 |
| `mcp_connection` | server_id, state, protocol_version, worker_id, pid_or_endpoint, started_at, last_error | 运行时状态（写 Redis 更合适，DB 留一份用于排障） |
| `mcp_invocation_log` | id, user_id, server_id, tool_id, params_redacted(JSON), status, duration_ms, error, created_at | 审计与用量统计 |
| `mcp_approval` | id, server_id, requester_id, approver_id, status, reason, decided_at | 接入审批流 |

**权限点建议新增**：`mcp:server:create`（自行接入）、`mcp:server:manage`（管理公共）、`mcp:tool:toggle`、`mcp:log:read`、`mcp:approval:approve`。

## 6. 里程碑与任务拆解

> 时间估算按 1 名开发「专注投入」估算，含自测。M0–M4 是 MVP 闭环，M5+ 是治理增强。

### M0 · 技术验证（3–5 天）——不写业务代码，只做探针

| 任务 | 验收标准 |
|---|---|
| 用 `mcp` 2.1.1 写最小脚本，连 stdio 服务器，打印 `protocol_version` 和 `tools/list` | 能跑通，确认当前协商到哪个协议版本 |
| 同样脚本连一个 Streamable HTTP 服务器 | 能跑通，确认 `Client(url)` 行为 |
| 人为连一个**只支持 2025-11-25 的老服务器**，验证自动降级 | 不报错，能拿到工具清单 |
| 验证 MRTR：触发一次"工具需要用户补充输入"，看现有 Agent 链路的表现 | 明确记录：现有 `planner/executor` 和人机确认流程是否会断，怎么补 |
| 验证并发：同时连 5 个 stdio 服务器，压测 100 次调用 | 无子进程泄漏，无死锁 |

**M0 的意义**：这几件事不验证清楚，后面的设计都是猜。特别是 MRTR 那条，会直接改写你 Agent 的确认流程。

### M1 · 数据层与配置迁移（约 1 周）

| 任务 | 验收标准 |
|---|---|
| 设计并落地 6 张表的 Alembic 迁移 | 迁移可升级可回滚 |
| 把现有 `MCP_SERVERS` 环境变量配置迁入数据库 | 迁移脚本 + 保留 env 回退（迁移期双读，DB 优先） |
| 服务器 CRUD API（后端） | 单元/集成测试通过 |
| 凭据加密存储（AES-GCM，主密钥复用现有 `secrets` 文件机制） | 密文入库，明文不落日志；主密钥可轮换 |
| `config.py` 改造：配置源从 env 切到 DB | calculator 服务器行为与改造前一致 |

### M2 · 连接运行时改造（1.5–2 周）——核心难点

| 任务 | 验收标准 |
|---|---|
| 按决策 1 方案 A 抽象连接编排层（接口先于实现） | 接口文档 + 单元测试（用内存假连接） |
| 动态启动/停止/重启单个服务器 | 不重启 Web 进程即可增删 |
| Streamable HTTP 传输支持 | 能接入一个远程 MCP 服务器 |
| 健康检测 + 自动重连 + 失败退避 | 杀掉子进程后能自动恢复；连续失败进入 `error` 状态并告警 |
| 优雅关停与子进程回收 | 压测后 `ps` 里无残留进程 |
| 子进程 stderr 日志采集落库/落文件 | 前端能看"这个服务器为什么起不来" |
| 工具清单发现 + 按 `ttlMs` 缓存 | 刷新机制生效，无重复全量拉取 |

### M3 · 权限、归属与审批（约 1 周）

| 任务 | 验收标准 |
|---|---|
| 接入决策 2 的 `owner_type` 归属模型 | 用户只能看到/操作自己的 + 有权的公共服务器 |
| 新增 5 个权限点并挂到现有 RBAC | 无权限的用户调 API 返回 403 |
| 审批流（可开关） | 开启后，用户接入需管理员审批；关闭时直接生效 |
| 凭据注入方式统一走 env（**禁止走命令行参数**） | 无凭据出现在进程列表/日志中 |

⚠️ **安全硬要求**：凭据绝不能作为命令行参数传递（`ps` / 任务管理器可见），必须通过环境变量或 stdin 注入。

### M4 · 前端管理控制台（约 1.5 周）

| 任务 | 验收标准 |
|---|---|
| 服务器列表页（公共 / 我的 双 Tab），展示状态、协议版本、工具数 | 状态实时（轮询或 SSE） |
| 新增服务器向导（选类型 → 填配置 → 填凭据 → 连通性测试 → 提交） | **保存前能一键测试连通并预览工具清单** |
| 服务器详情页：工具列表 + 单工具开关 + 启停/重启/删除 | 操作有确认弹窗 |
| 诊断面板：连接日志、最近错误、调用统计 | 出错时能自助排查 |
| 审批管理页（管理员） | 待办列表 + 通过/驳回 |

**M4 完成 = MVP 闭环**：用户能自助接入、看到工具、管起来。

### M5 · 治理增强（1–2 周）

- 调用审计日志（参数脱敏规则、结果摘要）+ 查询界面
- 限流与配额（按用户 / 按服务器 / 按工具）
- 危险工具策略：命中规则（如 `delete_*`、`*payment*`）强制二次确认
- 工具命名空间与冲突治理（撞名提示与处理）
- 批量导入：支持粘贴标准 `mcp.json` 一键导入多个服务器（你的 `~/.workbuddy/connectors/default/mcp.json` 就是现成测试样本）
- **上下文保护**：工具数量超阈值时改走"检索式按需注入"，不全量塞提示词

### M6 · 可选进阶（视需求再排）

- **对外网关端点**：把平台接入的工具聚合成一个 MCP 端点暴露给别的 AI 客户端（复用新规范的 `Mcp-Method` / `Mcp-Name` 头做路由）
- **内网适配**：npx/uvx 走内网镜像源、离线预置包（内网无外网时的刚需）
- **OIDC / 企业 IdP 对接**（EMA 方向）：管理员在 IdP 侧统一管控谁能用哪些 MCP 服务器，无需逐个授权
- 用量账单 / 成本归集

## 7. 风险清单

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | **多 worker 导致连接状态分裂** | 高，会推倒重来 | M1 前定死方案 A，接口按分布式设计 |
| 2 | **MRTR 改造影响现有人机确认链路** | 高 | M0 必须验证，别拖到 M2 |
| 3 | stdio 子进程泄漏 / 僵死 / 超时挂起 | 中高 | 统一超时、心跳、进程组 kill、压测验证 |
| 4 | 凭据泄漏（日志、进程列表、前端回显） | 高（安全事故） | 全链路脱敏；只走 env 注入；前端永不回显明文，只显示"已设置" |
| 5 | 工具数量膨胀压垮上下文 | 中 | M5 的检索式注入；默认按服务器分组折叠 |
| 6 | 内网无外网，`npx`/`uvx` 拉包失败 | 中 | 内网镜像源；或改为预置 Docker 镜像 |
| 7 | 第三方 MCP 服务器不可信（恶意工具、数据外传） | 高 | 审批流 + 工具白名单 + 出网限制 + 审计 |
