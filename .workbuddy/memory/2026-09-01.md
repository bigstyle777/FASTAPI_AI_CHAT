## 启动 backend/learn 的 mcp_client（已跑通）

问题：`backend/learn/mcp_client.py` 直接运行无输出。根因有三处。

1. `if __name__ == "__main__":` 被错误缩进写进了 `main()` 函数内部 → 脚本永不执行入口。
2. `StdioServerParameters(command="python", args=["learn/mcp_server_calculator.py"])` 依赖 CWD，
   且 Windows 上 `python` 可能解析到 Microsoft Store 存根 → 子进程启不来。
   改为 `command=sys.executable` + `Path(__file__).parent / "mcp_server_calculator.py"` 绝对路径。
3. 项目 `.venv` 装的是 **mcp 2.1.1**，而 server 用的是 1.x 写法 → `'Server' object has no attribute 'list_tools'`。
   mcp 2.x 中 `FastMCP` 已更名为 `MCPServer`（`from mcp.server.mcpserver import MCPServer`），
   改用 `@mcp.tool()` + `mcp.run(transport="stdio")` 后正常。

## MCP Python SDK 版本认知（重要，避免再次归因错误）

用户感叹"MCP2 怎么变得这么简单"，实际归因要纠正：
**变简单主要来自"低层 API → 高层 API"的切换，不是 1→2 的版本升级。**
- 低层 `Server`：手写 JSON Schema + 手动构造 `TextContent`，~21 行
- 高层 `MCPServer`（2.x）/ `FastMCP`（1.x）：只写带类型注解的函数，Schema 与返回包装
  由 SDK 从类型注解 + docstring 自动生成，~14 行
- 即：在 1.x 用 FastMCP 同样简单。真正让代码变短的是换到高层 API。

mcp 2.x 变更分四类（官方迁移指南 https://py.sdk.modelcontextprotocol.io/v2/migration/）：
1. 纯改名：FastMCP→MCPServer、McpError→MCPError、Content→ContentBlock、
   inputSchema→input_schema、structuredContent→structured_content（wire 层仍是 camelCase，
   手工序列化需 model_dump(by_alias=True)）
2. 依赖换血：httpx/httpx-sse→httpx2、协议类型拆到 mcp-types（被精确 pin ==mcp 版本，
   不要单独 pin）、新增 opentelemetry-api、资源 URI 由 AnyUrl 改为 str
3. 低层 Server 变严格（代码会变长）：装饰器 → 构造函数 `on_*=` 参数、
   返回值自动包装被移除、普通异常不再转 is_error=True
4. 新增能力：server.middleware 中间件、structured_content、资源模板 RFC 6570 + 路径安全

注意：2.x 中 `mcp.server.fastmcp` 被移除，导入会抛 ModuleNotFoundError 并带迁移链接。
当前项目已装 mcp 2.1.1 + mcp-types 2.1.1 + httpx2 2.12.0 + opentelemetry-api 1.44.0。

## MCP Tool 接入现有 Tool Calling 体系（完成）

目标：MCP Server 提供的 Tool 对 Agent 来说和本地 Tool 完全一样。

### 改动文件与职责
- `backend/app/agent/mcp_client.py`（核心，新建/完善）
  - `MCPTool`：保存 ClientSession + MCP tool name；`__call__(**kwargs)` 是 async，
    内部 `await session.call_tool(...)`；`_result_to_text()` 把 TextContent 拼成字符串
  - `mcp_tool_to_openai_tool()`：MCP name/description/input_schema → OpenAI function schema
  - `connect_calculator_server()`：stdio 拉起 `mcp_servers/calculator_server.py`，
    返回复用的 ClientSession（用 anyio BlockingPortal + wrap_async_context_manager 持有
    stdio_client / ClientSession 上下文，进入退出在同一后台任务内，满足结构化并发要求）
  - `discover_and_register_mcp_tools(all_tools, tool_registry)`：`session.list_tools()`
    动态发现，schema 进 ALL_TOOLS、MCPTool 实例进 TOOL_REGISTRY，重名跳过不覆盖本地工具
  - `close_mcp()`：逆序退出 session → stdio → portal，关闭子进程
- `backend/app/agent/tool_calling.py`：`_call_tool()` 增加 `inspect.isawaitable(result)`
  分支，协程交给 `run_coroutine_sync()` drain。主循环核心逻辑未动
- `backend/app/main.py`：lifespan 中启动连接 + 注册，关闭时 `close_mcp()`；
  MCP 失败只记日志不影响启动
- `backend/tests/test_mcp_tools.py`（新建，替代临时 verify_mcp_e2e.py）：8 个用例
- `requirements.txt`：补 `mcp==2.1.1`（此前只写了裸 `mcp` 未锁版本）

### 踩到的三个坑（重要）
1. **mcp 2.x 字段是 `is_error` / `input_schema`，不是 `isError` / `inputSchema`**。
   `getattr(result, "isError", False)` 在 2.x 恒为 False（别名只作用于 wire 层，
   不是 Python 属性），导致 MCP 错误永远检测不到。已改为先取 `is_error` 再回退 `isError`
2. **跨事件循环 await MCPTool 会挂死**：stdio 流与 ClientSession 绑定在
   BlockingPortal 的后台循环上，在别的循环（如 FastAPI 异步接口）里
   `await tool(...)` 直接超时不返回。解决：`__call__` 检测
   `asyncio.get_running_loop()`，非后台循环时走
   `asyncio.run_coroutine_threadsafe(...)` + `asyncio.wrap_future` 转交
3. 相对导入点数 = 文件所在目录的层级数（`app/main.py`→1 个点，`app/chat/services/x.py`→3 个点）

### 顺带修的既有 bug（非 MCP 引入）

memory/router、rag/parsers/*、rag/service、user/services/auth）。
