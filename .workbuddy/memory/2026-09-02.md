## mcp_client.py 改用 mcp 2.x 高层 Client API（重要更正）

用户质疑"你用的 mcp 版本是不是还是 1.x 的写法"，并贴出一段用 `mcp.Client` 的代码。
**实测证明他是对的**，我昨天用的 `stdio_client + ClientSession + initialize()` 三层是老写法。

### mcp 2.1.1 实测结论（都在本项目 .venv 里验证过）
- `from mcp import Client`：存在。`Client(server, ...)` 第一个参数可直接接收
  `StdioServerParameters`，也接受 `MCPServer` / `Transport` / str / `Server`
- `Client` **自带 initialize 握手**，不用再手动 `await session.initialize()`
- `Client` 是 async context manager（`__aenter__`/`__aexit__`），有
  `list_tools` / `call_tool` / `list_prompts` / `read_resource` / `session` 等
- `from mcp import MCPError`：存在，构造签名 `(code: int, message: str, data=None)`，
  实例有 `.code` / `.message` / `.data` / `.error`
- `ClientSession` + `stdio_client` **仍然可用、没有 DeprecationWarning**（不是废弃 API，
  只是啰嗦）。单层 `Client` 明显更短，已切换
- `Tool.input_schema`、`CallToolResult.is_error` 是 2.x 的 Python 属性名（1.x 是
  `inputSchema` / `isError`，且 1.x 里这两个字符串在 2.x 下 getattr 恒为 None/False）

### 改动
`backend/app/agent/mcp_client.py` 整体重写：
- `_session_cm` / `_stdio_cm` / `_mcp_session` 三个全局 → 只剩 `_client_cm` / `_mcp_client`
- `MCPTool.__init__` 保存 `client`（2.x 高层对象）而非 `ClientSession`
- `_call` 增加 `except MCPError` → 转成 `MCPToolError(error.message)`（协议层错误可读）
- `_result_to_text` 用 `isinstance(block, TextContent)` 替代 `block.type == "text"`
- 同步桥接（BlockingPortal + `run_coroutine_sync` + 跨循环转交）**保持不变**，
  因为 `execute_tool_call` 主循环是同步的

### 没有全盘照搬用户贴的代码，三点理由
1. `MCPClientManager`（多 server）→ 用户原始需求明确"只支持一个 server，
   不要引入 MCPClientManager"
2. 纯 async 设计（`_make_tool_caller` 返回 async 闭包）→ 接不进同步的
   `execute_tool_call`；用户原始需求要的是 "MCPTool 实例" 进 TOOL_REGISTRY
3. `AsyncExitStack` 管生命周期 → 在同步桥接场景下它的 `aclose()` 同样得在
   后台循环里跑，只持有一个上下文时用不上栈，手动 `__exit__` 更直白

test_planner 共 34 passed；子进程回收正常（连接中 +2，close 后回到基线）。
测试里 `tool.session` 断言已改为 `tool.client`。

## 调研：tool_calling 循环跑在哪（决定"改异步"是否紧迫）

结论：**技术债，不紧迫。而且只改 endpoint 不改内部会立刻变成灾难。**

### 实测查证（backend 目录）
- `app/chat/router.py` 12 个 endpoint、`app/agent/router.py` 3 个 endpoint
  → **全是 `def`，一个 `async def` 都没有**
- FastAPI/Starlette 把同步 endpoint 自动丢线程池；
  `StreamingResponse` 的**同步生成器**由 starlette/responses.py:233
  `iterate_in_threadpool` 也丢线程池 → **事件循环不会被阻塞**
- 线程池上限：anyio 默认 **40**（`current_default_thread_limiter().total_tokens`）
- Celery 只跑后台任务（memory 提取 / 标题生成 / RAG 文档解析），**不跑 tool calling**
- LLM 客户端是**同步** `OpenAI`（core/ai_client.py:34），不是 AsyncOpenAI
- `db` 是同步 SQLAlchemy Session

### 耗时实测（20 次平均）
- MCP 工具单次调用 **2.3 ms**，本地工具 ~0 ms
- 一次 LLM 调用 3~30 秒 → **MCP 占比不到万分之一**

→ 光把 MCP 改成异步收益为零，瓶颈全在同步的 OpenAI 客户端上。

### 危险陷阱（重要）
如果只把 endpoint 改成 `async def` 而内部仍是同步代码（OpenAI 同步客户端、
同步 SQLAlchemy Session），FastAPI 就**不再**丢线程池，同步阻塞直接跑在
事件循环上 → 一个请求就能卡死整个服务。比现在更糟。

### 正确重构顺序（将来真要改时）
1. `OpenAI` → `AsyncOpenAI`（收益 99.9%）
2. endpoint 改 `async def`
3. 同步 SQLAlchemy Session → async session（**硬性依赖**，否则查库也会阻塞事件循环，
   且 app 里到处是 `with SessionLocal() as db`，改动面很大）
4. MCP 那层**不用改**：已有后台循环，只占 2.3 ms

### 什么时候才必须改
并发打满 40 个线程时。SSE 流式接口（`chat_stream` / `agent_stream`）风险最高：
单个流式对话可能持续几十秒～几分钟占着一个线程，40 个并发流式对话就满了。

## 用户提的"同步/异步混用"改造方案：方向对，理由错一半

用户认为同步 tool calling 循环会卡住事件循环。**实测不成立**：全部 15 个
endpoint 都是 `def`，且 starlette 0.52 的 `StreamingResponse.__init__`
（responses.py:230-233）会把同步生成器包成 `iterate_in_threadpool`，
事件循环始终空闲。真正的代价是"每通对话独占一个线程 + 40 上限"和
"没法用 asyncio.gather 并行调工具"，不是事件循环被阻塞。

补充查证（本次新增）：
- `iterate_in_threadpool` 是**每个 item 各派发一次** `run_sync`
  （starlette/concurrency.py:53-55），所以同步生成器的执行会在线程池的不同
  线程之间漂移，而 `db` Session 是同步 SQLAlchemy、并非线程安全。目前靠
  "同一时刻只有一个线程在跑"侥幸没出问题，属于潜在隐患。
- 数据层全是同步：`create_engine("postgresql+psycopg://...")`（config.py:39）
  + `redis.Redis`。`is_stop_requested` 在 agent 循环里每步都调 Redis。
  → 只改 `async def` + AsyncOpenAI 而不动数据层，等于把阻塞的 DB/Redis
  搬到事件循环上，比现状更糟。这条早前记录已覆盖，本次再次确认。

- `MCPTool.__call__`（mcp_client.py:90-96）**已经**正确做了跨事件循环转交
  （`run_coroutine_threadsafe` + `asyncio.wrap_future`）。所以将来主循环改
  成 async 时，`run_coroutine_sync` 可以直接删，MCP 那层不用动。
