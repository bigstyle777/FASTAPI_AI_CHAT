## mcp_client.py 改用 mcp 2.x 高层 Client API（重要更正）

用户质疑"你用的 mcp 版本是不是还是 1.x 的写法"，并贴出一段用 `mcp.Client` 的代码。
**实测证明他是对的**，我昨天用的 `stdio_client + ClientSession + initialize()` 三层是老写法。

### mcp 2.1.1 实测结论（都在本项目 .venv 里验证过）
- `from mcp import Client`：存在。`Client(server, ...)` 第一个参数可直接接收
  `StdioServerParameters`，也接受 `MCPServer` / `Transport` / str / `Server`
- `Client` **自带 initialize 握手**，不用再手动 `await session.initialize()`
- `Client` 是 async context manager（`__aenter__`/`__aexit__`），有
  `list_tools` / `call_tool` / `list_prompts` / `read_resource` / `session` 等
- `from mcp import MCPError`：存在，构造签名 `(code: int, message: str, data=None)`，
  实例有 `.code` / `.message` / `.data` / `.error`
- `ClientSession` + `stdio_client` **仍然可用、没有 DeprecationWarning**（不是废弃 API，
  只是啰嗦）。单层 `Client` 明显更短，已切换
- `Tool.input_schema`、`CallToolResult.is_error` 是 2.x 的 Python 属性名（1.x 是
  `inputSchema` / `isError`，且 1.x 里这两个字符串在 2.x 下 getattr 恒为 None/False）

### 改动
`backend/app/agent/mcp_client.py` 整体重写：
- `_session_cm` / `_stdio_cm` / `_mcp_session` 三个全局 → 只剩 `_client_cm` / `_mcp_client`
- `MCPTool.__init__` 保存 `client`（2.x 高层对象）而非 `ClientSession`
- `_call` 增加 `except MCPError` → 转成 `MCPToolError(error.message)`（协议层错误可读）
- `_result_to_text` 用 `isinstance(block, TextContent)` 替代 `block.type == "text"`
- 同步桥接（BlockingPortal + `run_coroutine_sync` + 跨循环转交）**保持不变**，
  因为 `execute_tool_call` 主循环是同步的

### 没有全盘照搬用户贴的代码，三点理由
1. `MCPClientManager`（多 server）→ 用户原始需求明确"只支持一个 server，
   不要引入 MCPClientManager"
2. 纯 async 设计（`_make_tool_caller` 返回 async 闭包）→ 接不进同步的
   `execute_tool_call`；用户原始需求要的是 "MCPTool 实例" 进 TOOL_REGISTRY
3. `AsyncExitStack` 管生命周期 → 在同步桥接场景下它的 `aclose()` 同样得在
   后台循环里跑，只持有一个上下文时用不上栈，手动 `__exit__` 更直白

### 验证
`tests/test_mcp_tools.py` 8 passed；回归 test_tool_calling + test_agent_framework +
test_planner 共 34 passed；子进程回收正常（连接中 +2，close 后回到基线）。
测试里 `tool.session` 断言已改为 `tool.client`。

## 调研：tool_calling 循环跑在哪（决定"改异步"是否紧迫）

结论：**技术债，不紧迫。而且只改 endpoint 不改内部会立刻变成灾难。**

### 实测查证（backend 目录）
- `app/chat/router.py` 12 个 endpoint、`app/agent/router.py` 3 个 endpoint
  → **全是 `def`，一个 `async def` 都没有**
- FastAPI/Starlette 把同步 endpoint 自动丢线程池；
  `StreamingResponse` 的**同步生成器**由 starlette/responses.py:233
  `iterate_in_threadpool` 也丢线程池 → **事件循环不会被阻塞**
- 线程池上限：anyio 默认 **40**（`current_default_thread_limiter().total_tokens`）
- Celery 只跑后台任务（memory 提取 / 标题生成 / RAG 文档解析），**不跑 tool calling**
- LLM 客户端是**同步** `OpenAI`（core/ai_client.py:34），不是 AsyncOpenAI
- `db` 是同步 SQLAlchemy Session

### 耗时实测（20 次平均）
- MCP 工具单次调用 **2.3 ms**，本地工具 ~0 ms
- 一次 LLM 调用 3~30 秒 → **MCP 占比不到万分之一**

→ 光把 MCP 改成异步收益为零，瓶颈全在同步的 OpenAI 客户端上。

### 危险陷阱（重要）
如果只把 endpoint 改成 `async def` 而内部仍是同步代码（OpenAI 同步客户端、
同步 SQLAlchemy Session），FastAPI 就**不再**丢线程池，同步阻塞直接跑在
事件循环上 → 一个请求就能卡死整个服务。比现在更糟。

### 正确重构顺序（将来真要改时）
1. `OpenAI` → `AsyncOpenAI`（收益 99.9%）
2. endpoint 改 `async def`
3. 同步 SQLAlchemy Session → async session（**硬性依赖**，否则查库也会阻塞事件循环，
   且 app 里到处是 `with SessionLocal() as db`，改动面很大）
4. MCP 那层**不用改**：已有后台循环，只占 2.3 ms

### 什么时候才必须改
并发打满 40 个线程时。SSE 流式接口（`chat_stream` / `agent_stream`）风险最高：
单个流式对话可能持续几十秒～几分钟占着一个线程，40 个并发流式对话就满了。

## 用户提的"同步/异步混用"改造方案：方向对，理由错一半

用户认为同步 tool calling 循环会卡住事件循环。**实测不成立**：全部 15 个
endpoint 都是 `def`，且 starlette 0.52 的 `StreamingResponse.__init__`
（responses.py:230-233）会把同步生成器包成 `iterate_in_threadpool`，
事件循环始终空闲。真正的代价是"每通对话独占一个线程 + 40 上限"和
"没法用 asyncio.gather 并行调工具"，不是事件循环被阻塞。

补充查证（本次新增）：
- `iterate_in_threadpool` 是**每个 item 各派发一次** `run_sync`
  （starlette/concurrency.py:53-55），所以同步生成器的执行会在线程池的不同
  线程之间漂移，而 `db` Session 是同步 SQLAlchemy、并非线程安全。目前靠
  "同一时刻只有一个线程在跑"侥幸没出问题，属于潜在隐患。
- 数据层全是同步：`create_engine("postgresql+psycopg://...")`（config.py:39）
  + `redis.Redis`。`is_stop_requested` 在 agent 循环里每步都调 Redis。
  → 只改 `async def` + AsyncOpenAI 而不动数据层，等于把阻塞的 DB/Redis
  搬到事件循环上，比现状更糟。这条早前记录已覆盖，本次再次确认。

- `MCPTool.__call__`（mcp_client.py:90-96）**已经**正确做了跨事件循环转交
  （`run_coroutine_threadsafe` + `asyncio.wrap_future`）。所以将来主循环改
  成 async 时，`run_coroutine_sync` 可以直接删，MCP 那层不用动。

## 性能分析：一次 AI 聊天耗时大头（本次新增）

### 结论
- **普通聊天 `/chat/stream`：大模型生成占 97%+，自有代码（DB/Redis）合计仅 ~30 ms**
- **Agent `/agent/stream`：串行多次大模型往返，最坏 1 + 6×5 + 1 = 32 次，这才是大头**

### 实测数据（本机 Windows，Redis 未启动，用本地 TCP echo 模拟一次往返）
脚本：`AIChatPro/bench_chat_overhead.py`（用 `.venv/Scripts/python.exe` 跑）
```
Redis GET（一次网络往返，同步直连）        0.0846 ms/次
run_in_threadpool 空函数（纯调度）          0.2099 ms/次
run_in_threadpool + Redis GET（现状）      0.3574 ms/次
→ 每 token 的 0.357 ms 里，0.273 ms（76%）是线程池调度纯浪费
→ 500 token ≈ 0.18 s；2000 token ≈ 0.71 s
```

### 三个可优化点（按收益排序）
1. **历史长度无上限（最大隐患）**：`chat_ttl_seconds=3600`，Redis 上下文缓存
   过期后 `load_chat_context` → `load_visible_messages` → `get_messages_by_session`
   （repository/messages.py:152，**无 limit**）加载整个会话历史进 prompt。
   会话越长 → prefill 越长 → 首字延迟线性恶化。而缓存路径只保留 20 条
   （`save_chat_context` 的 `messages[-20:]`），两条路径不一致。
2. **每 token 一次 run_blocking**：`chat/services/messages.py:133`，
   `stream_ai_reply` 里每个 delta 都 `await run_blocking(is_stop_requested, ...)`。
   实测 0.357 ms/token，76% 是调度浪费。可改为每 N 个 token 查一次，
   或换 redis.asyncio 直接 await。
3. **Agent 步骤串行**：`agent/agent.py` 规划→逐步执行→总结严格串行，
   每步内部 `run_tool_loop` 最多 5 轮，每轮重发完整历史。

## 已实施：优化点 2 —— 停止检查改用 StopWatcher（进程内 + Redis 降频兜底）

### 方案选择（用户问"有没有比较好的方案"，给了 A/B/C 三选一）
- A 每 N 个 token 查一次 Redis：省 60~85%，停止延迟 N 个 token，改动 3 行
- B 换 redis.asyncio 直接 await：违背 blocking.py 里"数据层保持同步"的既定决策
- **C 进程内状态 + Redis 兜底（已采用）**：停止信号的写方（用户点停止）和
  读方（流式循环）在**同一进程**，放进程内存即可，一次集合查找是纳秒级。
  Redis 保留但降频成每秒一次兜底，将来扩多副本时最坏 1 秒内生效、不会静默失效

### 选型的关键依据
`docker-compose.yml` 里 backend 是**单容器单进程 uvicorn**（无 --workers），
所以进程内状态 100% 可靠。若将来加 --workers 或多副本，兜底会接管。

### 改动
- 新增 `backend/app/core/stop_signal.py`
  - 模块级 `_STOPPED_SESSIONS: set[int]` + `mark_stopped` / `clear_stopped`
    / `is_stopped_locally`（用可变集合，不做整体重新赋值，所以无需 global 声明）
  - `StopWatcher` 类：`should_stop()` 先查内存（免费），Redis 兜底按
    `_REDIS_FALLBACK_INTERVAL_SECONDS = 1.0` 降频；兜底命中时顺便写回本地
- `chat/services/messages.py`：`stop_generation_service` 加 `mark_stopped`；
  `stream_ai_reply` 用 StopWatcher 替换原来的每 token `run_blocking`；
  三个出口（开头、error 分支 return、正常结束）都清标记
- `agent/service.py`：同样接 StopWatcher 传给 `run_agent_stream(should_stop=...)`；
  `_resolve_run_status` 改为同步 + 只看本地标记（省一次 Redis）

### 实测收益（bench_stop_signal.py，2000 token）
```
旧写法   705.73 ms   查 Redis 2000 次   0.3529 ms/token
新写法     1.00 ms   查 Redis    1 次   0.0005 ms/token
```
合成场景省 99.9%（因为 2000 次循环 1 秒内跑完，兜底只触发 1 次）。
真实场景按每秒 1 次兜底估算：60 秒的回答约 21 ms，相对旧写法 706 ms 仍省 ~97%。

## 已实施：优化点 1 —— 喂模型的历史截断（条数 + 字符双上限）

### 关键前提：不能给 repository 加 limit
`get_messages_by_session` / `load_visible_messages` **必须保持全量**，因为
这两处需要完整数据：
- `messages.py:100` `get_messages_service` —— 前端展示全部历史
- `branch.py:23,64` `create_branch_service` —— 建分支要把原会话消息全量复制

所以截断只能加在**喂模型的那几条路径**上，不能动数据层。

### 方案
- `core/config.py` 新增两个设置：
  - `chat_context_max_messages: int = 20`
  - `chat_context_max_chars: int = 12000`（只限条数不够：20 条长文照样撑爆 prompt）
- `chat/services/message_context.py` 新增两个函数：
  - `trim_chat_messages(messages)` —— **从最新往回挑**，条数或字符预算用尽就停；
    `if picked and ...` 保证最新那条永不丢弃（否则用户刚问的问题会丢）。
    统一在 dict（role/content）层面处理，load 和 save 两条路径共用一份逻辑
  - `load_model_context(db, session_id)` —— 喂模型专用：
    `trim_chat_messages(to_chat_messages(load_visible_messages(...)))`
- 接入点（4 处喂模型的路径）：
  - `load_chat_context` 的 DB 回源分支 → `load_model_context`（chat 流式 + agent 都走这里）
  - `save_chat_context`：`messages[-20:]` → `trim_chat_messages(messages)`
    （原来硬编码 20 且无字符预算，与 DB 回源路径行为不一致，现在统一）
  - `send_message_service`（非流式）→ `load_model_context`
  - `modify_message_service` → 保持用 `get_messages_by_session`（不引入分支上下文，
    行为不变），外面套一层 `trim_chat_messages(to_chat_messages(...))`

### 效果（bench_context_trim.py 实测）
```
200 条 × 20 字符      5092 字符  →  520 字符（省 90%）
 30 条 × 2000 字符   60141 字符  → 10025 字符（省 83%）
500 条 × 3000 字符 1502892 字符  → 9018 字符（省 99.4%）
```
边界均已验证：单条超预算也保留 1 条、空历史不报错、顺序保持时间正序、
最新一条必保留。
