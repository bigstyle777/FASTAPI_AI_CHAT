- 官方 SDK Tier 1：TypeScript / Python / Go / C# 均已支持 2026-07-28（Go 为 go-sdk v1.7.0+，由 Google 协作维护）

### 规划中的三个关键决策（待用户拍板）
1. **连接放哪个进程**（最关键）：推荐方案 A——连接由单一专用进程/Celery worker 持有，Web 层经 Redis 发指令。因 uvicorn 多 worker 会导致 stdio 子进程状态分裂
2. **归属模型**：`owner_type = system | user` 并存，前端分「公共工具 / 我的工具」双 Tab
3. **工具进 Agent**：命名空间前缀 `mcp_<server_slug>__<tool_name>` + 冲突检测 + 按用户/角色过滤 + 单工具开关；工具数膨胀时改检索式按需注入（防爆上下文）

### 已识别的主要风险
多 worker 状态分裂、MRTR 影响现有人机确认链路、子进程泄漏、凭据走命令行参数会被 ps 看到、工具数量压垮上下文、内网无外网导致 npx/uvx 拉包失败、第三方 MCP 不可信。

## 探查：WorkBuddy「专家 / 技能 / 连接器」是怎么实现的（实地看 ~/.workbuddy）

**核心结论：三者不是三套系统，底层全是「插件 plugin」一种东西，靠命名前缀区分类型。**
证据 `~/.workbuddy/plugins/installed_plugins.json`：所有条目在同一个 plugins 字典下，前缀如 `skill-xxx`（技能）、`mcp-xxx`（MCP）、`interactionmode-xxx`（交互模式）、无前缀（综合插件）。每条记录 scope / installPath / version / installedAt / lastUpdated。

### 插件包结构（`plugins/cache/<市场>/<插件>/<版本>/`）
- `.codebuddy-plugin/plugin.json`：name / version / description / author / keywords / category（很轻）
- `skills/<name>/SKILL.md`：frontmatter 含 name、description、description_zh/en、version、**allowed-tools（工具白名单，权限最小单元）**
- `.mcp.json`：插件自带 MCP 服务器声明。两种写法——远程型 `{"url": ...}`；本地进程型用 `${CODEBUDDY_PLUGIN_ROOT}` 指回插件目录（如 weixinpay 用 `bin/run-node` 跑 `dist/mcp-server.mjs`）
- `agents/` `hooks/` `commands/`、`manifest.qmsig`（签名）、`.in_use/`（占用锁，防止运行时被删）、`.orphaned_at`（旧版本标记，延迟清理）
- 多版本共存于同一插件目录下，靠 installed_plugins.json 指向当前版本

### 技能的关键设计：按需加载
系统只常驻 name + description，判断用得上才把 SKILL.md 全文读入上下文 → 挂几十个技能也不撑爆上下文。**这正是我们 M5「工具太多压垮上下文」的同类解法：工具清单只存摘要，命中才加载完整 schema。**

### 连接器
- 市场条目极简：`connectors-marketplace/connectors/<name>/` 下只有 `mcp.json` + `skill/SKILL.md`
- 远程型只有 `{"timeout": 600, "url": "..."}`
- **作用域隔离**：`connectors/` 下并排 `default/` 和 `<账号ID>/`，`security/` 同样按账号 ID 分 → 配置与凭据天然按账号隔离
- 已启用状态在各自作用域的 `mcp.json`（`disabled: true/false`）

### 凭据加密方案（`connectors/<账号ID>/connector-states.json`，可直接抄）
```json
"encryption": {"scheme":"aes-256-gcm","kdf":"hkdf-sha256","salt":"...","userIdCheck":"...","keyCheck":"..."},
"version": 4, "connectors": {}, "envOverrides": {}, "headerOverrides": {},
"accountIdentityKey": "<userId>||enterprise"
```
- `userIdCheck` 防跨用户拷贝凭据文件；`keyCheck` 让主密钥错误可明确报错
- `envOverrides` 与 `headerOverrides` 分开存放，正对应 MCP 的 env 与 headers 两种注入方式
- `version` + 多个 `xxxMigrated: true` 布尔标记 → 一次性幂等迁移

### 对我们 MCP 平台的直接借鉴
1. 归属模型不用做两套：加 `scope = system|user`，配置与凭据按 scope 隔离（照抄 connectors/ 目录分法）
2. M1 凭据加密照抄 aes-256-gcm + hkdf + userIdCheck + keyCheck
3. M2 照抄 `.in_use` 占用锁（连接在用不许删）与 `.orphaned_at`（旧版本延迟清理）
4. M3 权限粒度照抄 `allowed-tools`：工具级白名单，不只是服务器级
5. M5 防爆上下文照抄技能按需加载
6. 版本迁移照抄 `version` + `xxxMigrated` 幂等标记

注：本地未找到 experts 实体目录，推测专家是云端目录 + 走同一套插件检索安装机制（推断，未证实）。

## 终局形态定义（M0–M6 全完成后的成品，待用户确认）

新增前端页面 `frontend/src/views/McpView.vue`（对齐现有 ChatView/AdminView/KnowledgeView/MemoryView 的 Vue3+Tailwind 风格），路由 `/mcp`，含 4 个 Tab：公共工具 / 我的工具 / 接入审批 / 调用审计。

**三视角定义**
- 普通员工：在 ChatView 里无感使用，Agent 自动选工具；无权限时引导一键申请；自助接入流程「填配置 → 测试连接（预览发现的工具数）→ 保存 → 立即可用」，不重启服务
- 管理员：看全局状态（在线/异常/工具数/协议版本）、单个工具级启停、高危工具（`delete_*`、退款类）默认二次确认、审批、审计可追溯
- 系统内部：专用进程持有全部连接；Web 层经 Redis 发指令；编排层启停子进程/HTTP 连接、拉 tools/list、写库、回状态；定时体检+自动重连；调用链为「鉴权→限流→高危拦截→执行→审计」；凭据密文入库，主密钥在服务器文件，前端只显示"已设置"

**能力边界（已向用户明示，不要过度承诺）**
- 做不到：不可信第三方 MCP 的安全沙箱（另一量级工程）；自动理解工具语义与冲突消解（仍靠模型）；内网无外网时 npx 类服务器仍需运维预置；防不住用户主动把机密贴给外部工具（属 DLP 范畴）

**一句话定位**：让 AIChatPro 从"AI 只会聊天"变成"AI 能安全地碰公司系统，且每笔操作可追溯"。
